A cell's checkpoint (`mushin_resume.last_ckpt`) is handed only to an attempt under the config and task code that wrote it. A re-run whose config or task code changed (same swept values, another fixed value) was handed the previous run's checkpoint, right after mushin warned that it re-ran the cell for that change; with Lightning, restoring a finished run's `last.ckpt` skips training, so the old weights' metrics were recorded for the new config (#391). Such a cell now trains from scratch, with `is_resume` still True. To continue from the old checkpoint on purpose (a raised `max_epochs`), load it from `mushin_resume.dir` yourself. A config holding a resolver whose value changes from run to run (`${now:...}`) changes the fingerprint each run, so its cells are not handed a checkpoint across runs; a requeued attempt of the same run still is.
