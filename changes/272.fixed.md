mushin's own console output no longer fails with `UnicodeEncodeError` on a console that cannot encode what it prints (a Windows pipe in cp1252, a cp437 console, `PYTHONIOENCODING=ascii`). `show`, `diff` and the `dry_run=True` preview print a metric name or other value outside the console's encoding as a backslash escape such as `\u03b1`, with the table's columns still aligned, while the returned `.table` keeps the text itself. `python -m mushin guide --path` prints only a real path: one the console's encoding cannot represent goes out as the path's own bytes when stdout's encoding is the file system's, and otherwise (a Windows pipe in cp1252, for one) the command exits with status 1 and a message saying how to widen stdout. The text files mushin writes are UTF-8 on every platform, and mushin reads them as UTF-8. With `on_error="nan"`, a cell whose error message the locale's encoding lacked no longer ends the sweep, since `mushin_error.txt` is now UTF-8; the MCP server's `get_failures` reads it as UTF-8, falling back to the locale's code page for a file an earlier release wrote (in UTF-8 mode too). `capture_env=True` decodes uv's output as UTF-8: decoded in the locale's encoding, it raised on any non-ASCII byte under an ASCII locale, and under cp1252 on characters such as Á whose UTF-8 holds a byte the code page leaves undefined, and the snapshot then silently fell back to the bare package list. The default `metric_load_fn` reads a JSON metrics file as UTF-8, UTF-16 or UTF-32, with or without a byte-order mark (such a file went to `torch.load` and failed), and falls back to the locale's code page, so a UTF-8 file no longer reads garbled on Windows. Provenance records a non-ASCII git branch name as UTF-8. mushin's own console text, warnings and error messages are now plain ASCII; the dry-run preview opens with `Dry run: N cells`. `target_job_dirs` naming a file now says the path is not a directory rather than that it does not exist.
