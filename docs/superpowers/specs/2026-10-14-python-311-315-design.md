# Design: drop Python 3.10, prepare Python 3.15

**Date:** 2026-10-14
**Status:** Revised after adversarial review. Next: the implementation plan,
[`2026-10-14-python-311-315.md`](../plans/2026-10-14-python-311-315.md).

## Problem

Python 3.10 reached end-of-life on **2026-10-01**, and Python 3.15.0 was
released on **2026-10-09** (both dates from <https://devguide.python.org/versions/>).
mushin declares `requires-python = ">=3.10"`, tests 3.10–3.14, and advertises
"3.10 – 3.14". So it should stop supporting 3.10 and start supporting 3.15.

Dropping 3.10 is mechanical. **Supporting 3.15 is blocked upstream today.**
The facts below were measured on 2026-10-14. They decide how far this change
can go.

## Facts established

### Dropping 3.10

- **Lock diff is clean.** Raising `requires-python` to `>=3.11` and running a
  plain `uv lock` (no `--upgrade`) removes exactly 13 versions that were locked
  only for 3.10: `async-timeout`, `contourpy 1.3.2`, `exceptiongroup`,
  `ipython 8.39.0`, `matplotlib 3.10.9`, `netcdf4 1.7.3`, `networkx 3.4.2`,
  `numpy 2.2.6`, `rpds-py 0.30.0`, `scikit-learn 1.7.2`, `scipy 1.15.3`, `tomli`
  and `xarray 2025.6.1`. It upgrades nothing, and the resolution markers go
  from 17 to 14.
- **Code that 3.11 makes obsolete.** At `target-version = "py311"`, ruff
  reports two sites:
  - `src/mushin/workflows.py:21`: `from typing_extensions import Self`. `Self`
    is in `typing` from 3.11. This is the only `typing_extensions` import in
    `src/`, `tests/`, `examples/` and `scripts/`.
  - `src/mushin/_provenance.py:145`: `timezone.utc` becomes `datetime.UTC`.

  There are no `sys.version_info` gates and no `tomli` or `exceptiongroup`
  imports anywhere.
- **The Dependabot netCDF4 ignore is now obsolete.** `.github/dependabot.yml`
  ignores netCDF4 minor and patch bumps because netCDF4 >= 1.7.4 needs
  numpy >= 2.3 on Windows ARM64, and numpy 2.3 needs Python >= 3.11. That made
  the (3.10, ARM64, win32) lock split unsatisfiable. The comment ends "Revisit
  when requires-python moves past 3.10." With `>=3.11`, a scratch copy whose
  netCDF4 floor is raised to `>= 1.7.4` locks without error.
- **Intel macOS keeps one Python.** Intel macOS is pinned to torch 2.2.x and
  NumPy 1.x, and the support matrix lists it as "3.10 – 3.11". Without 3.10,
  **3.11 is the only Python supported on Intel macOS.** This change does not
  revisit that row's upper bound; see Non-goals.
- **Every floor still holds on 3.11.** The full suite was run at
  `--resolution lowest-direct --extra eval` on 3.11, with `setuptools<81` and
  `--no-sync`, on both dependency branches:
  - NumPy-2 branch (arm64 macOS: numpy 2.0.0, torch 2.4.1, scipy 1.13.0,
    pandas 2.2.2, matplotlib 3.9.0, xarray 2024.6.0, scikit-learn 1.4.2,
    netCDF4 1.7.1.post1): **752 passed, 12 skipped**.
  - Intel-mac branch (x86_64 macOS: torch 2.2.0, numpy 1.24.0, same
    pure-Python floors): **749 passed, 15 skipped**.

  The `min-versions` CI job (Linux x86_64) remains the authoritative check.
- **`make test-lowest` does not do what it says.** It runs
  `uv sync --resolution lowest-direct --extra eval && uv run pytest ...` with
  the repo bind-mounted.
  - The plain `uv run` sees a lock that does not match the default resolution,
    so it re-locks at highest and re-syncs. The suite therefore runs against
    the newest versions, not the floors. `ci.yml` warns about exactly this,
    which is why `min-versions` uses `--no-sync`.
  - The bind mount means the host's `uv.lock` is rewritten.
  - It also omits the `setuptools<81` step that `min-versions` has.
  - Found in review and reproduced there.

### Python 3.15

Three separate blockers:

1. **hydra-zen 0.17.0 does not import on 3.15.**
   `hydra_zen/typing/_implementations.py:9` does
   `from dataclasses import _MISSING_TYPE`. CPython 3.15 reimplemented
   `dataclasses.MISSING` as a PEP 661 sentinel (`MISSING = sentinel("MISSING")`)
   and removed `_MISSING_TYPE`. A plain `pytest tests/` stops with
   `Interrupted: 44 errors during collection`. Every module that imports
   mushin at module scope fails. The 19 modules that collect would all error
   at setup anyway, because the autouse fixture in `tests/conftest.py` imports
   mushin. With `-n` or `--continue-on-collection-errors` this shows up as 198
   errors.
   - **Upstream fix:** hydra-zen PR #903, "Fix import on Python 3.15 (0.17.1)",
     by the maintainer. Opened 2026-10-13, all CI green, including a 3.15 leg,
     and awaiting review. It is not released.
2. **PyPI has no cp315 torch.** torch 2.14.1 on PyPI ships cp310–cp314 only,
   and torchvision 0.29.1 the same. mushin hard-depends on torch, so
   `pip install mushin-py` cannot resolve on 3.15.
   - PyTorch's own index (`https://download.pytorch.org/whl/cpu`) does carry
     torch 2.14.1 and torchvision 0.29.1 cp315 wheels for linux x86_64 and
     aarch64, win_amd64 and macOS arm64.
3. **The macOS and Windows cp315 torch wheels crash.** On macOS arm64,
   torch 2.14.1 cp315 from the PyTorch index segfaults (rc -11/139) when it
   exits after any autograd work, even
   `torch.nn.Linear(4, 1)(torch.randn(2, 4)).sum().backward()`. Just importing
   it is fine.
   - **Upstream:** this is pytorch/pytorch#200779. The macOS and Windows cp315
     wheels were built against 3.15.0b3 headers, and `PyThreadState` changed
     layout in b4, so pybind11's `gil_scoped_acquire` writes to the wrong field.
     It was closed on 2026-10-14 as "fixed in nightly and upcoming 2.15"
     (pytorch/pytorch#199356).
   - **Linux is unaffected.** On the official `python:3.15-slim-bookworm`
     image, the same script exits 0.

There is also a fourth problem, found in review, that matters only at
promotion time:

4. **The universal lock does not give 3.15 wheels.** In the `>=3.11` lock, uv
   resolves scipy for the Intel-mac fork first (numpy<2). scipy 1.18.x needs
   numpy>=2, so uv settles on scipy 1.17.1 and reuses that version in every
   fork, including the one that covers 3.15.
   - scipy 1.17.1 ships cp311–cp314 only. 1.18.1 ships cp312–cp315.
   - Neither `uv lock --upgrade-package scipy` nor a fresh lock changes this.
   - contourpy 1.3.3 has the same problem.
   - So a lock-based 3.15 leg would build scipy from source, even after torch
     ships cp315 wheels.

**mushin's own code is 3.15-clean once those are fixed.** In a Linux 3.15.0
container, with torch 2.14.1+cpu from the PyTorch index and hydra-zen from
PR #903's head (`1e5d8de`), the full suite gives **762 passed, 1 failed,
5 skipped**.
- The one failure is `test_git_dirty_is_unknown_when_status_fails`. It asserts
  `out["sha"] is not None  # we ARE in a git repo`, and the container held a
  `git archive` export with no `.git`. That is the environment, not 3.15.
- On macOS arm64 the same setup gives 761 passed and 2 failed. Both failures
  are the torch exit segfault in a child process.

## Decisions

### D1. Drop 3.10 completely

- `requires-python = ">=3.11"`, and remove the 3.10 classifier.
- CI: take 3.10 out of the `test` matrix. Move the Intel-mac leg and the
  `min-versions` job to 3.11, since it is now the oldest supported Python.
- Makefile: `test-lowest` uses `ghcr.io/astral-sh/uv:python3.11-bookworm-slim`.
  The target is fixed while it is being touched, so that it actually mirrors
  `min-versions`:
  - It bind-mounts the repo **read-only** at `/src` and works on a copy, so the
    host `uv.lock` is never rewritten.
  - It installs `setuptools<81`.
  - It runs pytest with `uv run --no-sync`.
  - It installs `git` in the container. `test_git_dirty_is_unknown_when_status_fails`
    asserts it runs inside a git checkout, and the copy keeps `.git`.
- ruff `target-version = "py311"`, and apply its two fixes.
- pyproject comments whose rationale is 3.10-specific are reworded:
  - The matplotlib floor note ("that also ships Python 3.10 wheels; lower
    floors ... fail to build on 3.10") keeps only the NumPy-2 reason. The floor
    itself is unchanged.
- Two remarks tie the optional `mcp` SDK to "Python >= 3.10": the
  `mcp/server.py` docstring and the `importorskip` comment in
  `tests/test_mcp/test_server.py`. That version gate no longer explains
  anything, because every supported Python satisfies it. The guard is there
  because `mcp` is an optional extra, so the remarks say that instead.
- Remove the `typing-extensions` runtime dependency. Its only use was `Self`.
  torch requires `typing-extensions` itself, so environments still have it;
  mushin just stops declaring a dependency it does not use.
- Remove the Dependabot netCDF4 ignore. Its own comment asks for that
  revisit, and the revisit (above) shows the reason is gone. The torch, numpy
  and torchvision comment just below it says their failure "was masked by the
  netCDF4 error above". That is reworded so it still makes sense once the
  netCDF4 entry is gone.
- Docs:
  - README and `docs/install.md` say 3.11 – 3.14.
  - The Intel-mac row becomes "3.11".
  - The "Python 3.9 is not supported" note becomes a 3.10 note with its EOL
    date.
  - `CONTRIBUTING.md`'s matrix sentence was already stale ("3.9–3.14"); it is
    corrected.
- Changelog: one `removed` fragment, written for users. It names the
  Intel-mac consequence.

### D2. Do not advertise 3.15 yet

No 3.15 classifier. README and the install guide do not list it as
supported. The install guide gets a short **Python 3.15** note: it is not
supported yet, here is why (the three blockers, each linked), and what will
change that.

**Why not claim it now:**
- `pip install mushin-py` fails on 3.15 (blocker 2).
- It could not import even if installed (blocker 1).
- On macOS and Windows, the only cp315 torch that exists crashes (blocker 3).

A classifier would promise something no user can get. The repo's own bar,
stated when 3.14 was added (#179), is "advertise it only once that leg is
required to pass". No 3.15 leg can pass today.

**Alternatives rejected:**
- *Classifier plus "install torch from the PyTorch index first" docs.* Still
  broken on macOS and Windows, which is blocker 3, and still broken everywhere
  until hydra-zen 0.17.1.
- *A marker floor, `hydra-zen >= 0.17.1 ; python_version >= '3.15'`.* 0.17.1 is
  not on PyPI, so this cannot be locked. Dependabot also cannot update
  marker-split declarations (see the torch and numpy note in `dependabot.yml`).
  The floor is raised globally at promotion instead (D4).

### D3. Add a 3.15 preview workflow (code compatibility only)

A separate workflow, `.github/workflows/python-315-preview.yml`, that is
**not** part of `ci.yml` and **not** a dependency of `ci-ok`. It answers one
question: **does mushin's code work on 3.15?** It does not ask whether mushin
is *installable* on 3.15 from PyPI with the committed lock. That is the
promotion question (D4), and the answer is known to be "no" until upstream
moves.

- **Triggers:**
  - `workflow_dispatch`, which works once the file is on `main`.
  - `pull_request` with `paths: ['.github/workflows/python-315-preview.yml']`,
    so any PR that adds or edits this file runs it. That includes this PR,
    which is how it gets exercised before merge, since `workflow_dispatch`
    cannot run a workflow that is not on the default branch yet.
  - No `schedule`; see "Rejected" below.
- **Matrix:** `ubuntu-latest`, `windows-latest` and `macos-latest`, the same
  three platforms as the 3.14 legs, with `fail-fast: false` so that one leg
  failing does not cancel the others. Intel-mac stays out, since torch 2.2.x
  has no cp315 wheels.
- **Steps:**
  1. `uv venv --python 3.15`
  2. `uv pip install torch torchvision --index-url https://download.pytorch.org/whl/cpu`
     (the only cp315 torch that exists)
  3. `uv pip install -e ".[eval,detection,image,audio]" --group dev`, with
     everything else resolved fresh from PyPI. The torch already installed
     satisfies the requirement, so it is kept. The lock cannot be used: it
     pins torch from PyPI (no cp315) and scipy 1.17.1 (no cp315); see
     blocker 4.
  4. `uv run --no-sync pytest tests/ --hypothesis-profile fast -p no:cacheprovider`

**Why a separate workflow, not experimental legs in `ci.yml`:**
- **Standing red.** A failing `continue-on-error` job still shows as a failed
  check on every PR. That would last for weeks while upstream is blocked, on
  every PR including Dependabot's. The repo explicitly rejects standing reds:
  `dependabot.yml` silences a known-failing updater "so the next genuine
  failure is visible instead of buried under a standing red".
- **No cancelled main runs.** `ci.yml`'s concurrency group
  (`ci-${{ github.workflow }}-${{ github.ref }}`, `cancel-in-progress`) would
  let a manual dispatch on `main` cancel an in-flight `main` push run. A
  separate workflow has its own group.
- **Cheap to dispatch.** Dispatching the preview runs just the three 3.15 legs,
  not the whole CI.

**Expected state at merge:** on this PR, the preview check is red on all three
legs, and it is not required.
- Each leg should reach step 4, which proves the venv and both installs work.
- Then pytest should stop with the hydra-zen `_MISSING_TYPE` collection
  errors.
- If any leg fails *before* step 4, that is a plumbing bug, and it is fixed
  before merge.

**Rejected: a scheduled tripwire.** The first draft also ran the preview
weekly and opened an issue when every leg passed. Review found three problems:
- **It can fire early.** It tests PyTorch-index torch, so it can pass while
  PyPI still has no cp315 torch (D4 criterion 2).
- **It tests the wrong environment.** Promotion ships the universal lock,
  which blocker 4 makes non-installable from wheels.
- **It is noisy.** It would have gone red every week, with nothing telling
  "still blocked" apart from "newly broken".

Simpler signals are already coming:
- Dependabot opens a lock-bump PR when hydra-zen 0.17.1 ships, since hydra-zen
  is not on its ignore list.
- torch 2.15 is the other prerequisite. When it ships, the promotion checks in
  D4 are a single command each.

### D4. Promotion: a later PR, with these criteria

Promote when **all** of these hold:
1. **hydra-zen >= 0.17.1 is on PyPI.**
2. **torch and torchvision have cp315 wheels on PyPI** for linux x86_64,
   win_amd64 and macOS arm64, and they do not hit pytorch#200779. Check for
   each platform with:

   ```
   uv pip compile pyproject.toml --python-version 3.15 \
       --python-platform <x86_64-manylinux_2_28 | x86_64-pc-windows-msvc | aarch64-apple-darwin> \
       --only-binary torch --only-binary torchvision
   ```

   Then run the preview workflow (dispatch on `main`); it must pass on all
   three legs.
3. **The committed lock installs on 3.15 from wheels.** This means solving
   blocker 4 first.
   - scipy must resolve to a version with cp315 wheels (>= 1.18.1) for 3.15.
     That needs either a marker-split requirement, for example
     `scipy >= 1.18.1 ; python_version >= '3.12' and (sys_platform != 'darwin' or platform_machine != 'x86_64')`,
     or a uv fork setting. Note that a bare `; python_version >= '3.15'` marker
     still fails, because the Intel-mac numpy<2 fork has no Python bound.
     Also note that Dependabot cannot update marker-split declarations (the
     torch and numpy note in `dependabot.yml`), so this trade-off has to be
     weighed then.
   - The same goes for contourpy 1.3.3, and for every other locked version
     that lacks cp315 wheels at that point.
   - Verify with `uv export --frozen ... | uv pip compile - --python-version 3.15 --only-binary :all:`
     on each of the three platforms.

The promotion PR then:
- Raises the hydra-zen floor to `>= 0.17.1`, with a comment. 0.17.0 cannot
  import on 3.15, and a global floor avoids a marker split.
- Adds "3.15" to `ci.yml`'s blocking matrix: ubuntu, windows and macos-arm64,
  locked via `uv sync`.
- Bumps the locked torch, torchvision and numpy to versions with cp315 wheels,
  by hand, since Dependabot ignores them.
- Adds the 3.15 classifier, sets README and the install guide to 3.11 – 3.15,
  and removes the install-guide 3.15 note.
- Deletes `python-315-preview.yml`.
- Adds an `added` changelog fragment.

## Non-goals

- **Intel-mac on 3.12.** torch 2.2.2 and numpy 1.26.4 both publish cp312
  macOS x86_64 wheels, which suggests the install guide's "Python 3.12+ is not
  available there" may be stale. Re-testing that row is separate work.
- **Free-threaded 3.15t.**
- **Notebook outputs.** The committed outputs in `docs/notebooks/*.ipynb` show
  provenance from a 3.10 kernel (`"python": "3.10.19"`). They are display-only:
  `nbmake` re-executes them, and regenerating them is unrelated churn.
- **Historical documents.** Nothing under `docs/superpowers/` older than this
  spec is touched. They are historical records.
- **The `latest-deps.yml` failure report.** It files its issue with
  `--label latest-deps`, and that label does not exist, so the report step
  fails (seen in runs 38397832554 and 38546255658) and no issue has ever been
  filed. The bug is real but unrelated to Python versions, so it gets a
  separate fix.
- **Other lock refreshes.** No floor raises other than those above, and no
  unrelated lock bumps. One example: the locked `pandas 3.0.4` is yanked for
  datetime segfaults. That is a separate, Dependabot-shaped fix.

## Verification

- **`make check` equivalent:** ruff lint and format, codespell, and the full
  suite on the default interpreter.
- **Full suite on 3.11** (`uv run --python 3.11`), the new floor.
- **Lock diff by package against `origin/main`:** only the 13 3.10-only
  versions removed, nothing upgraded. Check this *before* any lowest-direct
  run, as an independent check.
- **The fixed `make test-lowest`** (Docker, amd64). Check that:
  - pytest runs at the floors, by looking at the printed versions;
  - it passes;
  - the host `uv.lock` is byte-identical afterwards.
- `mkdocs build --strict`.
- **`actionlint`** on the edited and new workflows, if available.
- **The preview workflow's run on this PR:** every leg reaches the pytest step
  and fails only with the hydra-zen `_MISSING_TYPE` collection errors.
- **Normal PR CI:** `ci-ok` green, Intel-mac leg on 3.11, `min-versions` on
  3.11.
