# Drop Python 3.10, prepare 3.15: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make Python 3.11 the floor and remove every trace of 3.10. Add a
non-required Python 3.15 preview workflow, and say plainly in the docs why
3.15 is not supported yet.

**Architecture:** This is a version bump in metadata, CI and docs, with the lock
regenerated by a plain `uv lock`. 3.15 gets its own workflow, outside `ci-ok`.
It installs torch from PyTorch's index (PyPI has no cp315 torch) and resolves
everything else fresh. The design and every decision are in
[the spec](../specs/2026-10-14-python-311-315-design.md). Read it first.

**Tech Stack:** uv, GitHub Actions, ruff, towncrier, pytest, Docker for the
amd64 lowest-direct mirror.

**Conventions (from repo history and memory):**
- Never credit Claude in commits or PRs.
- Never run a bare `uv lock --upgrade`. Regenerate with plain `uv lock` and
  diff by package against `origin/main`.
- Changelog fragments start as `changes/+slug.<type>.md`. Rename them to
  `changes/<PR>.<type>.md` once the PR number exists.
- Commit style is `type(scope): summary`, as `git log` shows.

### Task 4: Add the Python 3.15 preview workflow

**Files:**
- Create: `.github/workflows/python-315-preview.yml`

- [ ] **Step 1: Write the workflow.**

  ```yaml
  name: Python 3.15 preview

  # Does mushin's code work on Python 3.15? This is NOT a supported-version leg
  # (3.15 is not advertised yet) and NOT part of ci.yml's required `ci-ok`. It
  # is expected to fail until upstream catches up, and a standing red in the
  # required CI would bury real failures.
  #
  # Blockers as of 2026-10-14:
  #   - hydra-zen 0.17.0 does not import on 3.15 (Python 3.15 removed
  #     dataclasses._MISSING_TYPE). Fixed by hydra-zen#903, to ship as 0.17.1.
  #   - PyPI has no cp315 torch. PyTorch's own index does, and this workflow
  #     installs from it, but its macOS/Windows cp315 wheels crash
  #     (pytorch#200779). Fixed in torch 2.15.
  #
  # This answers "does the code work", not "is it installable from PyPI with
  # the committed lock". That is the promotion question, with its own
  # checklist: docs/superpowers/specs/2026-10-14-python-311-315-design.md, D4.
  # Promotion moves 3.15 into ci.yml's matrix and deletes this file.

  on:
    workflow_dispatch:
    # workflow_dispatch only works once this file is on the default branch. A
    # PR that adds or edits the file runs it, so changes to it are exercised
    # before merge.
    pull_request:
      paths:
        - ".github/workflows/python-315-preview.yml"

  permissions:
    contents: read

  concurrency:
    group: python-315-preview-${{ github.ref }}
    cancel-in-progress: true

  jobs:
    test:
      runs-on: ${{ matrix.os }}
      strategy:
        # Every leg is expected to fail for now; one failing must not cancel
        # the others, or we learn nothing about them.
        fail-fast: false
        matrix:
          # The platforms the 3.14 legs cover. Intel-mac is absent: it caps at
          # torch 2.2.x, which has no cp315 wheels.
          os: [ubuntu-latest, windows-latest, macos-latest]
      steps:
        - uses: actions/checkout@v7
        - uses: astral-sh/setup-uv@v7
          with:
            enable-cache: true
        - name: Create a Python 3.15 virtual environment
          run: uv venv --python 3.15
        - name: Install torch and torchvision from the PyTorch CPU index
          # The only cp315 torch builds; PyPI's torch stops at cp314.
          run: uv pip install torch torchvision --index-url https://download.pytorch.org/whl/cpu
        - name: Install mushin with the battery extras and the dev group
          # Resolved fresh, not from uv.lock: the lock pins PyPI torch and
          # scipy 1.17.1, neither of which has cp315 wheels. The torch
          # installed above satisfies mushin's requirement, so it is kept.
          run: uv pip install -e ".[eval,detection,image,audio]" --group dev
        - name: Show resolved environment
          run: uv pip list
        - name: Run tests
          # --no-sync: run in the venv built above; never re-resolve uv.lock.
          run: uv run --no-sync pytest tests/ --hypothesis-profile fast -p no:cacheprovider
  ```

### Task 5: Fix and move `make test-lowest`

**Files:**
- Modify: `Makefile:26-30`

- [ ] **Step 1: Replace the `test-lowest` recipe.** Replace the whole target
  (its help line stays the same) with:

  ```make
  test-lowest: ## Run the suite against the LOWEST declared dep versions (x86_64 Linux via Docker; mirrors the min-versions CI job)
  	docker run --rm --platform linux/amd64 -v "$(PWD)":/src:ro -e UV_LINK_MODE=copy \
  		ghcr.io/astral-sh/uv:python3.11-bookworm-slim \
  		bash -c "apt-get update -qq && apt-get install -y -qq git >/dev/null \
  			&& mkdir /app && tar -C /src --exclude=./.venv --exclude=./.git -cf - . | tar -C /app --no-same-owner -xf - \
  			&& cd /app && git init -q && git add -A && git -c user.name=test-lowest -c user.email=test-lowest@localhost commit -qm snapshot \
  			&& uv sync --resolution lowest-direct --extra eval \
  			&& uv pip install 'setuptools<81' \
  			&& uv run --no-sync pytest tests/ --hypothesis-profile fast -p no:cacheprovider"
  ```

  Each piece answers one of the review findings:
  - **No host writes.** `/src` is mounted read-only and the work happens on a
    copy at `/app`, so the host `uv.lock` is never rewritten.
  - **No `UV_PROJECT_ENVIRONMENT`.** `uv sync` puts the venv at `/app/.venv`,
    where both `uv pip install` and `uv run --no-sync` find it. `uv pip`
    ignores `UV_PROJECT_ENVIRONMENT`, so the old `/opt/venv` setting would
    make the `setuptools` step fail with "No virtual environment found".
  - **Floors stay floors.** `--no-sync` keeps pytest at the floors instead of
    re-locking to highest, and `setuptools<81` matches `min-versions`.
  - **A fresh git snapshot.** It replaces copying `.git`, so the provenance
    test (`out["sha"] is not None`) always runs inside a checkout, even from a
    linked worktree, where `.git` is a file pointing at a host path the
    container cannot see. `--no-same-owner` makes the copy root-owned, so git
    does not reject it as "dubious ownership".
  - **`.venv` is excluded.** It is the host's macOS environment, about 1 GB and
    useless in the container. Gitignored build output (`site/`, `multirun/`)
    is copied but is not part of the snapshot commit.

  Makefile recipe lines must start with a **tab**.
